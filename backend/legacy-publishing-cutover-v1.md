# Legacy publishing cutover v1

Date: 2026-10-21. Source: `brief/project.json` v104, approved A2 creator import and A4 owner publication contracts, current starter source and the unmodified Lovable export at `integration/lovable-raw-v1`. **Read-only audit and proposal. No application code or external service changed.** Frontend and Backend must agree a prospective cutover contract before implementation.

## Finding

No raw Lovable React/Supabase client is imported into the active Next.js application. The raw export's `src/integrations/supabase/client.ts`, its hooks, admin pages, and `supabase/functions/translate` remain outside `starter` and must not be copied into the active runtime. The Supabase runtime still present in `starter` comes from the earlier TicketNest publishing implementation. It is separately gated, while the currently visible public creator route uses anonymous Vercel Blob demo publication. The new canonical path is **conversation draft → brand selection/sign-in → private Neon draft → owner review → A4 Neon publication → `/events/{id}`**. That path exists in code but connected Clerk/Neon/media verification is still pending; legacy Blob remains the public catalog today.

## Supabase and Lovable remnants

`.env.example` still advertises `PUBLISHING_ENABLED`, `SUPABASE_URL`, `SUPABASE_ANON_KEY`, and `SUPABASE_SERVICE_ROLE_KEY`. Their joint flag is false by default, but setting all values would re-enable a second production publication path. `database/setup.sql`, `CONNECTION-HANDOFF.txt`, `backend/verify-v2.mjs`, older contracts and generated `content/site.json` describe that historical system; they are not evidence that Supabase is connected now. The raw Lovable export contains many direct Supabase hooks (checkout, affiliates, analytics, check-in, seat picker, forms, etc.) and a Lovable AI translation function. No active starter code imports that client. Adopt features through the agreed Neon API/schema, never by copying those hooks or keys.

## Required prospective interface agreement

1. **Creator completion:** define one final CTA and stable handoff contract from `/creator` to `/dashboard?source=creator` and `/events/new?source=creator`. Decide whether the review button stays for local review while the publish button becomes “Save to brand draft,” or collapses into one action. Preserve `ticketnest-draft` and its images on every failed/partial transfer. A successful import redirects to the private draft, not `/listing/{id}`.
2. **Legacy write closure:** define the exact response for `POST /api/demo/listings` after cutover, what happens to an in-flight `clickatick-publish-intent-*` retry, and whether a tested pre-cutover replay still returns its original result. Prevent new anonymous Blob listings without breaking already shared URLs/receipts. Confirm any marketing-workspace behavior tied to creator-token cookies before closing writes.
3. **Catalog/read cutover:** agree the public home/discover source, pagination/search, error state, and URL scheme. Existing Blob `/listing/{id}` and `/receipt/{id}` can remain read-only archives; canonical new events use `/events/{id}` and A4 receipts. Confirm whether old demos remain discoverable or only work by direct link. Keep `NEXT_PUBLIC_NEON_DEMO_CATALOG_ENABLED` off until connected checks; remove the dual-section state during cutover.
4. **Auth/API cleanup:** after creator/local paths no longer call them, retire `/api/auth`, `/api/listings`, the `database()/session()` Supabase helpers and `PUBLISHING_ENABLED`/`SUPABASE_*` example entries. Separate AI/speech capabilities and `sameOrigin` so removing Supabase does not interrupt conversation, speech, demo historical reads or marketing.

These are interface and sequencing choices for PM/Frontend/Backend, not requests to reconnect Supabase. Owner-approved sign-in before **new** publication, owner-only review, private media retention and demo-only checkout already determine the core behavior. No further owner question is needed for the technical cutover unless the visibility of old listings is treated as a product decision.

## Safe deprecation order and proof

1. Freeze and test the current creator local draft, voice/chat, and legacy Blob read/receipt paths. Confirm existing direct links work and no service connection is implied by a local fixture.
2. Agree the four interface items above. Implement creator handoff and Clerk/Neon import first; verify canceled sign-in, brand switch, idempotent import replay, mapping warnings, local photo recovery, and retained device copy.
3. Verify the A4 owner publish path with connected Clerk/Neon/private media and a real browser: owner succeeds, editor is denied, missing pin/photo/disclaimer blocks publication, retry reuses key, `/events/{id}` renders and zero-charge demo quote/checkout returns a receipt. Leave gates off if any connected part fails.
4. Switch marketplace/discover to Neon as canonical; keep old Blob read-only route and receipts. Close new anonymous Blob publication and old local/Supabase publication in the same release once callers no longer use them. Check old links, retry response and current catalog search/pagination.
5. Remove orphaned Supabase/local auth/data code and environment examples after `rg` confirms no runtime imports. Keep `sameOrigin`, AI/speech capability and any validation still used by the legacy read or creator draft. Archive historical SQL/docs as evidence rather than running them on Neon. Run focused route/storage tests, full check/build, then browser journeys on phone and desktop before claiming cutover.

No migration script should bulk copy old Blob listings or raw Lovable Supabase rows without an explicit ID, ownership, media and receipt mapping. Historical receipts are immutable demos; no real sale, admission or payment exists to migrate.
