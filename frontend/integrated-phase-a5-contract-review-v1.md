# Frontend review — Phase A5 storefront and staff contract v1

Date: 2026-10-21. Reviewed against `brief/project.json` v104 and `frontend/integrated-phase-a5-ux-v1.md`. No A5 code changed.

**Frontend accepts the A5 scope and route direction, subject to the interface amendments below.** The stable `/organizers/{organizerId}` storefront, current brand name, A4 `PublicEventSummary` reuse, private-link invitation, and owner-only team writes fit the approved product. Keeping email delivery disabled is honest. Published revisions, seat authoring and demo activity correctly remain separate contracts.

## Amendments before Frontend and Backend code

1. **Make owner permissions explicit in the storefront edit response.** The contract says edit controls are server-projected, but its `GET /organizers/{id}/storefront` example has no role or permissions. Add `permissions:{editStorefront:boolean,manageTeam:boolean}` or an exact active-member role. Frontend should not infer write authority from a visible URL or a separate possibly stale request. The server still enforces every mutation.
2. **Define both profile conflict versions.** Storefront PATCH checks `expectedBrandVersion` and `expectedProfileVersion`, while the shared error envelope mentions only `currentVersion`. Return `{currentBrandVersion,currentProfileVersion}` or a named `currentVersions` object on 409 `VERSION_CONFLICT`; say whether the client should refetch both. Same-key replay must return its original projection even if another edit followed it, so the UI can explain stale data without overwriting newer work.
3. **Specify team pagination and projection by role.** The owner team list promises bounded pages but the response has no cursors or query parameters. Define separate member and invitation cursors, page limits and sort order, or separate list routes. Include member `version` in owner rows so role/status PATCH can send `expectedVersion`. State the exact viewer/editor projection, such as `{ownMembership,memberCount}` with no Clerk IDs. Loading more members must not repeat or skip rows when invites change.
4. **Prefer an opaque membership ID in the mutation path.** `PATCH /members/{clerkUserId}` requires exposing provider subjects and careful path encoding. A stable membership UUID in the owner list and route is simpler and keeps Clerk identifiers server-side. If Backend keeps the Clerk subject, explicitly specify encoded-path validation, a display-safe member label, and whether owners can distinguish otherwise anonymous members. This is an interface choice, not a change to the role model.
5. **Complete invitation recovery states.** Define the owner list's returned invitation status and safe display text for `created`, computed `expired`, `revoked`, and `accepted`; include `nextCursor`. For an accept retry after a lost response, same subject/key must return the committed dashboard URL before the used-token check. A different key used by the same subject should have a defined recovery path, or the UI should direct them to `/dashboard` without claiming the link is still active. Specify 409/410/revoke conflict codes and `Retry-After` for 429 so the screen can give one clear next action.

## UI and release boundary

The public storefront can render brand details, separately paged active events, a factual empty state, a labelled media fallback, and distinct 404/503 states. Name edits must leave the stable URL intact. The owner editor can show text fields while logo/banner controls remain disabled until A3's media contract and public delivery are verified. No brand badge, custom domain or payment claim belongs on the page.

The team screen should show private-link creation and revocation only after the invite gate and connected Clerk/Neon/secret checks pass. `Copy link` is a browser action, never a server `sent` state. An email form may explain that delivery is not connected; it must not imply an invitation was sent. The accept page shows brand and role before sign-in, preserves the validated return path through Clerk, and confirms membership only from the POST response. A disabled member cannot regain access merely by opening an old invitation.

PM product choices still needed are limited to existing disabled-member reactivation policy and when branding media may leave its gate. The owner has already decided stable generated storefront IDs and both private-link and emailed staff invitations; do not ask again. Keep `STOREFRONT_ENABLED` and `STAFF_INVITES_ENABLED` off until connected browser/API/database checks, including mobile and keyboard states. A4 public event and legacy Blob routes stay unchanged.
