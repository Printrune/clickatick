# Frontend review — Phase A3 media v3

Date: 2026-10-21. Reviewed `contract/integrated-phase-a3-media-v3.md` against `brief/project.json` v104, `integration/design/brand-media-v1.md`, and the current private-media panel. No app code changed.

**Frontend agrees with the storage and security direction, subject to the interface amendments below before parallel implementation.** V3 correctly supersedes the old image-only 100 MiB model, keeps the owner's 100-image and 10-video brand maxima, respects the shared free Blob allowance, and fails closed when whole-store use cannot be accounted for. The conservative 950 MB admission threshold is an operational safety margin, not an owner-approved separate brand allowance. Public playback stays hidden until format, delivery and range behavior are verified. The narrow SDK exposure of an opaque private upload pathname is necessary for direct client upload and must remain isolated from public DTOs.

## Contract amendments needed

1. **Reserve the actual token maximum, not merely a declared minimum.** The intent reserves `sourceBytes`, but the proposed token text permits `maximumSizeInBytes=100000000`. A client could declare 1 MB and upload 100 MB. Set the token's maximum to the intent's exact declared `sourceBytes` (bounded by 100,000,000), and reject/quarantine completion if Blob `head().size` exceeds that reservation. Define behavior when the transferred file is smaller, and use actual bytes only after verification. The browser cannot choose a new size for the same `uploadId`.
2. **Return non-ready assets in the brand list.** `GET /assets` limited to ready/deleting cannot support the design's `Needs attention` filter or recovery after a reload on another device. Include pending, uploading, verifying and failed records in an authenticated, bounded list, with no private pathname. Specify state sort and cursor/filter behavior. The status-by-ID route then handles polling; the list restores IDs and retry choices after refresh.
3. **Define exact `AssetSummary` and error DTOs.** Frontend needs `id`, media type/kind, state/version, display name, source and stored bytes, MIME, alt text, created/updated times, preview availability, reference count, and an optional failure code/message safe to display. Define whether `usage` accompanies both intent and status under the normal `{data,error}` envelope. Specify field paths and retry codes for brand item limit, shared store full, unknown usage, unsupported format, expired intent, conflicting upload ID, and callback verification failure. `Retry-After` is useful only when the route actually sends it.
4. **Clarify video destination before a public placement exists.** `kind:"event-video"` with `eventId:null` should create an unassigned private brand-library video, or `eventId` should be required. State explicitly that the current A2 event draft has no video attachment/publish readiness until a later contract defines placement, poster and captions. The UI can upload and inspect a private library item once the video gate passes, but it must not show an active event-video module or imply public playback.
5. **Give the frontend a capability response.** The present `NEXT_PUBLIC_PRIVATE_MEDIA_ENABLED` gate is all-or-nothing. V3 can enable images and private videos at different times. Add server capability fields in usage or a separate endpoint, such as `imageUploadEnabled`, `videoUploadEnabled`, `videoPlaybackEnabled` and a short reason. The UI must derive controls from server truth, with any public environment flag only a conservative extra gate. This prevents an enabled button from calling a route still intentionally disabled.

## Ready-for-code boundary

Existing `PrivateMediaPanel` still checks a 2 MiB image limit and shows image-only library language. It is gated off today. Replace those values and copy only after PM settles the new image source/output cap and Backend agrees the image write contract. Keep required business/event photos and the current `/creator` local-image recovery intact. In the new brand library, display server-reported item counts, shared remaining bytes and freshness; if usage is unknown, disable upload and leave inspection/delete available. Preserve the selected File and upload ID through recoverable network failure, distinguish successful private upload from successful event attachment, and never infer success from a browser progress bar alone.

**Owner decisions still queued through PM, one at a time:** image source/output cap; exact video container/codecs and public playback timing; poster/captions; upload rate/concurrency. Published media replacement is covered in principle by the owner's later in-place edit decision, but its immutable-history and receipt-reference rules need a separate versioned contract. Do not re-ask the approved item limits, 100 MB video maximum, free shared Blob choice, or retention until explicit deletion.

No connected Vercel Blob inventory, SDK callback, private video Range response, or browser upload was tested in this review. Keep all writes and playback gated until those checks pass.
