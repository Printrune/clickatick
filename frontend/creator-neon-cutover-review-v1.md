# Creator-to-Neon cutover, Frontend review v1

Date: 2026-10-21. Brief: `brief/project.json` v104. Reviewed `contract/creator-neon-cutover-v1.md`, `backend/legacy-publishing-cutover-v1.md`, and current creator, dashboard, import, homepage and discover callers. This is a prospective review. No application code changed.

**Agree with the core journey.** Keep the anonymous voice/text conversation and local review. Handoff to explicit brand selection, import a private Neon draft under Clerk identity, and let the owner publish only after A4 validation. Retain the device draft and local photos through every partial failure. New public events use `/events/{id}` and the zero-charge demo checkout. The old Supabase/local session must not authorize a Neon write.

I need these amendments before implementing the cutover:

1. **Make the brand selection actionable for current roles.** `/api/v1/me` may return owner and editor brands, but the current A2 import path and editor accept only owners. During creator import, show eligible owner brands as selectable. Show other brands with a clear unavailable explanation, or omit them with a clear reason. If no eligible owner brand exists, offer brand creation rather than sending an editor to an expected 403. Keep the normal dashboard brand chooser unchanged.
2. **Define old-link behavior consistently.** The contract calls Blob listings a read-only archive, yet it also preserves legacy demo checkout and historical marketing behavior. Say exactly whether `/listing/{id}` permits a new demo checkout/receipt, artwork generation, or marketing mutation after cutover. If any write remains, do not describe that listing as read-only. Protect old receipts and existing listing links regardless. Frontend needs the correct call to action and disclosure on the old detail page.
3. **Finish the catalog flag and activation order.** Name one server-owned cutover gate, define whether an old client sees the previous creator or a closed-write recovery state during a rolling deployment, and pair new creator assets with the 410 backend response before turning it on. The single Neon catalog must not expose a pagination control that only searches or filters the first fetched page. Specify first-page size and `nextCursor` handling, or explicitly label the search as limited to loaded events. Remove `NewDemoCatalog` in the same cutover.
4. **Resolve the pending archive visibility choice through the PM.** The proposed default, old Blob listings absent from new `/discover` but reachable by their direct links, is coherent. It is not yet an owner decision, so no catalog implementation should assume it.

One UI detail should be retained in the contract: local review and “Save to brand draft” are separate actions. The current review editor lets the creator inspect or correct details before brand selection. The handoff button should be available from that review, and should never claim publication. The obsolete login dialog and anonymous publish control can be removed in the same client release that has the brand handoff and recovery path.

The implementation sequence should first prove local draft restoration and creator import with a canceled Clerk sign-in, owner brand choice, two brands, and network retry. Then verify connected owner publication, media/pin validation and demo checkout. Only after that should the PM enable the canonical Neon catalog and close the old anonymous write paths as one coordinated release. This review does not claim those connected checks have passed.
