# Integrated promotions and referrals contract v3

Date: 2026-10-21. Prospective under `brief/project.json` v107. Supersedes v2 after `frontend/integrated-promotions-referrals-review-v1.md` and `backend/integrated-promotions-referrals-v2-acceptance-v1.md`. Final Frontend and Backend agreement is required before code. The owner approved a 10% platform fee and an organizer-funded referral percentage, both calculated on the discounted ticket price. This contract concerns a zero-charge demo. It promises no payment, admission, delivery, promo redemption, earned commission, or payout.

## Scope and calculation

One ticket-only promotion and one referral attribution can apply to each quote. A promotion reduces the buyer ticket price. A referral never changes that price. Add-ons, taxes, and processing fees are excluded pending separate owner decisions. Integer cents and integer basis points are authoritative. Given server-stored tier prices, calculate `originalTicketSubtotalMinor`; percentage discount is `floor((originalTicketSubtotalMinor*basisPoints+5000)/10000)`, or fixed discount is `min(amountMinor,originalTicketSubtotalMinor)`. Clamp discount to the original subtotal. Let `discountedTicketSubtotalMinor=originalTicketSubtotalMinor-discountMinor`; `platformFeeMinor=floor((discountedTicketSubtotalMinor*1000+5000)/10000)`; `organizerShareBeforeReferralMinor=discountedTicketSubtotalMinor-platformFeeMinor`; `referralRewardMinor=min(organizerShareBeforeReferralMinor,floor((discountedTicketSubtotalMinor*referralBasisPoints+5000)/10000))`; `organizerShareAfterReferralMinor=organizerShareBeforeReferralMinor-referralRewardMinor`. The published event version owns the referral rate, capped at 9,000 basis points by A2. Every value is nonnegative and the cents reconcile. This is an illustration, not a ledger entry. At $55.00, 20% off, and 10% referral, the discounted ticket price is $44.00, the fee and reward are $4.40 each, and the organizer remainder is $35.20 before unallocated costs. Demo `amountChargedMinor` is 0.

## Database and permissions

Migration creates `organizer_promotions(id UUID, organizer_id UUID, event_id UUID NULL, code_normalized TEXT, kind, basis_points NULL, amount_minor NULL, minimum_original_subtotal_minor, maximum_real_redemptions NULL, active, expires_at NULL, version, created_at, updated_at)`. Enforce exactly one discount value matching `kind`; percentage `1..10000`, fixed amount `1..100000000` cents, minimum `0..100000000`, maximum real redemptions positive if set, version positive. Normalized code is uppercase ASCII `A-Z0-9` plus hyphen, length `4..32`, trimmed before validation, with `UNIQUE(organizer_id,code_normalized)`. Do not rely on locale-specific uppercasing. Add a unique `(organizer_id,id)` on public events if not already present and composite `FOREIGN KEY (organizer_id,event_id) REFERENCES public_events(organizer_id,id)` for non-null event scopes. Referenced promotion rows remain for historical quotes; deactivation replaces physical deletion.

Migration also creates `organizer_referral_codes` with UUID, organizer UUID, event UUID, normalized code with the same length/alphabet, active, version, timestamps and composite event FK. Codes are unique across both promo and referral namespaces **within an organizer**, enforced by a shared code registry or one transaction-safe namespace table; the implementation may use a single code table with a `kind` discriminant. Do not rely on application-only collision checks. No promoter name, email, buyer identity, earnings, payable balance, or payout details are stored in this demo. Since the owner has not settled who owns a customer referral code, demo creation belongs to the organizer and has no payable beneficiary. Do not claim that this fulfills the eventual customer referral scheme.

Active brand owner may create, edit, activate, and deactivate promotions and referral codes. Active editor may create or edit an inactive draft but cannot activate, deactivate, or change an active code; owner reviews and activates. Viewer cannot mutate. Every private route derives Clerk subject server-side and scopes `(organizer_id,event_id)` in queries. Foreign ID returns 404; insufficient role returns 403. Public APIs never enumerate codes or reveal a beneficiary.

## Exact private API

All responses use A4/A6 `{data,error}`. Private GET list routes `/api/v1/organizers/{org}/promotions` and `/api/v1/organizers/{org}/published-events/{eventId}/referral-codes` take `?cursor=<opaque>&limit=1..50`, default 20, order `(created_at DESC,id DESC)`, and return `{data:{items:[CodeSummary],nextCursor:string|null},error:null}`. `CodeSummary` for promotion is `{id,code,kind:"percentage"|"fixed",basisPoints:number|null,amountMinor:number|null,eventId:string|null,minimumOriginalSubtotalMinor:number,maximumRealRedemptions:number|null,active:boolean,expiresAt:string|null,version:number,createdAt:string,updatedAt:string}`. Referral summary is `{id,code,eventId,active,version,createdAt,updatedAt}`. No demo-use or revenue counter is returned.

POST `/promotions` accepts exactly `{idempotencyKey:UUID,code,kind,basisPoints,amountMinor,eventId,minimumOriginalSubtotalMinor,maximumRealRedemptions,expiresAt}`. Nullable members must be explicit; creation is **inactive**. POST `/published-events/{eventId}/referral-codes` accepts exactly `{idempotencyKey:UUID,code}` and also creates inactive. Both return 201 `{data:{item:CodeSummary},error:null}`; same key and canonical body replay returns 200 with the identical item, changed body with same key returns 409 `IDEMPOTENCY_CONFLICT`. The idempotency claim and row insert share one transaction.

PATCH `/promotions/{id}` accepts exactly `{expectedVersion:number,idempotencyKey:UUID,changes:{code?,kind?,basisPoints?,amountMinor?,eventId?,minimumOriginalSubtotalMinor?,maximumRealRedemptions?,expiresAt?}}`. PATCH referral code accepts `{expectedVersion,idempotencyKey,changes:{code?}}`. Optional change keys mean leave unchanged; explicit null clears nullable values. Both reject an empty `changes` object and edits to active codes with `CODE_ACTIVE`; owner must deactivate first. POST `/{id}/activate` and POST `/{id}/deactivate` accept exactly `{expectedVersion,idempotencyKey}` for owner only. Activation validates current terms, event brand, expiration and version. Deactivation is idempotent only for the same key/body; new key on already inactive returns 409 `ALREADY_INACTIVE`. Mutations return `{data:{item:CodeSummary},error:null}` with 200 for PATCH/activation/deactivation and exact same-key replay. Stale version returns 409 `{data:null,error:{code:"STALE_VERSION",message,currentVersion}}`; duplicate code returns `CODE_CONFLICT`; invalid input returns 422 with `fields:[{path,code,message}]`. Same-origin bounded JSON, UUID parsing and no secrets in errors apply throughout. No DELETE endpoint in v3.

## Buyer input, quote, and versioned write path

The A4/A6 quote POST body changes atomically with Frontend callers to exactly `{idempotencyKey:UUID,occurrenceId:UUID,items:[...],promoCode:string|null,referralCode:string|null}`. For a coordinated migration, absent codes are parsed as null; empty or whitespace code is normalized to null, so all three forms have the same canonical idempotency hash. Reject unknown keys and malformed nonempty codes. A code presented on `/events/{eventId}?ref=CODE` populates the referral input only; never send price, fee, discount or promoter identity from the browser. Keep the A4/A6 same-origin, 16 KiB request limit and existing seat/quantity checks.

Any unknown, inactive, expired, wrong-event, below-minimum or malformed **nonempty** promotion code returns HTTP 422 `{data:null,error:{code,message,fields:[{path:"promoCode",code,message}]}}`. The same classes of referral-code error use `path:"referralCode"`. The outer code may distinguish `PROMO_INVALID`, `PROMO_EXPIRED`, `PROMO_NOT_APPLICABLE`, or `REFERRAL_INVALID`, but must not reveal whether a code exists in another brand. Inline field feedback is required even if a general message is also returned. A quote that changes *after it was issued* uses the separate `code_changed` read state and 409 `QUOTE_CHANGED` checkout recovery; neither is a 422 field error.

When `PROMOTIONS_DEMO_ENABLED=false`, submitting a nonempty `promoCode` returns HTTP 503 `{data:null,error:{code:"PROMOTIONS_UNAVAILABLE",message:"Promo codes are unavailable in this demo."}}`. When `REFERRALS_DEMO_ENABLED=false`, a nonempty `referralCode` returns HTTP 503 `{data:null,error:{code:"REFERRALS_UNAVAILABLE",message:"Referral codes are unavailable in this demo."}}`. If both nonempty codes are submitted while both gates are off, return `PROMOTIONS_UNAVAILABLE` first. Null, missing, empty and whitespace codes canonicalize to null, so existing no-code quotes still work when the gates are off. The route never silently ignores a submitted nonempty code.

`lib/integrated-phase-a4-runtime.mjs` now has `demoWriteHandlers()` choosing A6 `createVersionedQuote` and `checkoutVersionedQuote` while `PUBLISHED_REVISIONS_ENABLED=true`. Promotions must extend **that A6 pair** and use `public_version_tiers`, `public_version_seats`, `public_version_inventory_pools`, `public_event_versions.snapshot`, and `public_events.active_version`; do not create a parallel A4 price path. When revisions are off, existing A4 quote/checkout remains unchanged and promotional controls stay off. An integration test must prove the dispatcher calls A6 for writes, not only reads, before either promotion flag can turn on.

Server resolves code existence, same-brand and event scope, active state, expiry and minimum **original** subtotal within the quote transaction. Configured `maximumRealRedemptions` is informational in demo. Demo checkout never increments it, and demo quote validation must never say it was exhausted. Future real-use limits require a verified payment ledger and atomic redemption design before use. No client-calculated discount is trusted.

The immutable quote contains its A6 `eventVersion` and a `terms` snapshot: `promotion:null|{id,version,code,scopeEventId,kind,basisPoints,amountMinor,minimumOriginalSubtotalMinor,maximumRealRedemptions,expiresAt}` and `referral:null|{id,version,code,scopeEventId,referralBasisPoints}`. It also has `pricing:{originalTicketSubtotalMinor,discountMinor,discountedTicketSubtotalMinor,platformFeeMinor,organizerShareBeforeReferralMinor,referralRewardMinor,organizerShareAfterReferralMinor,currency:"USD"}`. For the coordinated cutover, legacy `ticketSubtotalMinor` means **discounted** subtotal; `organizerShareMinor` means after referral; `platformFeeMinor` mirrors `pricing`. `amountChargedMinor:0`, `demo:true`, and `seatSelectionReserves:false` remain. No published price or quote field is mutated after issue. The quote response remains `{data:{quote,checkoutUrl},error:null}` with 201 for new and 200 replay.

`GET /api/v1/events/{eventId}/demo-quotes/{quoteId}` preserves the original quote and adds `state:"code_changed"` and `recovery:{code:"QUOTE_CHANGED",detailUrl:"/events/{eventId}"}` when either referenced code is missing, deactivated, expired, has changed `version` or scope, or the event referral rate changed. Priority: cancelled event, changed event version, code changed, expired quote, past occurrence, ready. Keep A6 `event_changed` recovery and no-store headers. A newly invalid code never recalculates the stored price. Same-key successful checkout replay returns the original receipt before any current checks. A new checkout checks A6 event version, then promotion/referral terms against their frozen IDs and versions, then quote expiry and occurrence. Any changed code returns 409 `QUOTE_CHANGED` with `detailUrl`; an active A6 version change uses `EVENT_VERSION_CHANGED` and its existing recovery fields. The demo checkout writes no redemption, sale, referral earning or seat reservation.

The receipt copies `terms` and `pricing` from the quote into both top-level response and A6 immutable `eventSnapshot`, alongside the original event title, occurrence, restrictions, price and version. It remains `{data:{receipt,receiptUrl},error:null}`, `amountChargedMinor:0`, `admissionValid:false`, `referralPayoutConnected:false`. Existing no-PII direct-link receipt retention and event cancellation notice remain. Historical receipts never recalculate pricing when a code or event changes. Frontend shows the original/discounted breakdown for new receipts and preserves the existing display for old receipts without `pricing`.

## UI, gates and tests

Private organizer UI lists and edits promo codes, with a visible owner review/activation action. The event page shows one promo input and the referral attribution from the link. Quote and checkout show original price, discount, discounted ticket price, and no-charge demo notice; no action says a customer paid or a promoter earned money. Invalid code feedback stays next to its field. On small screens, the discounted price and demo notice appear before the checkout action.

`PROMOTIONS_DEMO_ENABLED=false` and `REFERRALS_DEMO_ENABLED=false` by default; both require `PUBLISHED_REVISIONS_ENABLED=true`. Public activation requires connected Clerk/Neon, migration applied, owner/brand scope proof, A6 write-path proof, browser quote-to-receipt check, mobile check, and no-charge language review. Disabled UI hides controls and disabled private routes return 503 with an explicit capability error. No payment or payout service is activated by these flags.

Tests use a migrated database and cover fee/reward rounding, mixed GA/seats, percent/fixed/100% codes, minimum original subtotal, case normalization and namespace collisions, scope and active-state checks, owner/editor permissions, stale version, idempotent replay, term edit/deactivation/expiry between quote and checkout, demo use limit remaining unchanged, A6 version switch, immutable receipt after edit/cancel, invalid code recovery with exact `fields[].path`, nonempty code 503 capability errors while flags are off, 0 charged, and absence of PII/admission/payout. Frontend and Backend agree exact DTOs and route ownership before code.

Unresolved owner product choices for **real-money** launch: whether add-ons are discountable, processing fee allocation, multiple stacked promos, who may own a referral code and self-referral policy, tax calculation, provider, refunds and chargebacks, and post-event payout method. The demo's one promo plus one referral, ticket-only discount, and no payable beneficiary are scoped assumptions, not owner decisions about live commerce.
