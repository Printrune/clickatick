# Integrated Phase A3 media v5 — image direct-upload amendment

Date: 2026-10-21. Source `brief/project.json` v104, PM handoff 008, agreed `contract/integrated-phase-a3-media-v4.md`, and the current Frontend media work. **Prospective only.** This v5 amends v4 where images used an old multipart Function route. All other v4 rules remain, including the 100-image/10-video brand maxima, 100 MB video cap, 950,000,000-byte shared-store admission ceiling, complete-store accounting, explicit delete retention, and disabled feature gates. Frontend agreement and PM handoff are required before code.

## Why the image path changes

A 10,000,000-byte image cannot pass through the old `POST /assets` multipart route because Vercel Functions cap request/response bodies at 4.5 MB. The browser uploads the source image directly to the **private** Vercel Blob store using the same reserved-intent/client-upload protocol as video. The Function receives only a bounded JSON intent and SDK callback. The server then reads the private source Blob, decodes it, strips metadata, re-encodes it to an allowlisted image format, writes a normalized private Blob of at most 5,000,000 bytes, verifies both physical objects, and marks the asset ready. It returns small JSON status, never image bytes in the upload response. Existing A2/A4 media references use the normalized asset, not the source.

Vercel's current Function body limit is documented at [Vercel Functions limits](https://vercel.com/docs/functions/limitations), and direct client uploads at [Vercel Blob client uploads](https://vercel.com/docs/vercel-blob/client-upload). Connected SDK behavior must still be tested before activation.

## Exact image intent and browser handoff

`POST /api/v1/organizers/{org}/assets/upload-intents` accepts the existing v4 shape with `mediaType:"image"`, `kind:"business"|"event-location"|"cover"|"poster"`, `sourceName`, `sourceMime:"image/jpeg"|"image/png"|"image/webp"`, integer `sourceBytes` 1–10,000,000, `uploadId:UUID`, and `eventId:UUID|null`. `eventId:null` creates an unassigned brand-library image; a brand-owned event ID records context but does not attach to a draft. Source names are display-only, sanitized and bounded. Server validates brand owner, image count, rate/concurrency limits, complete global usage, and immutable upload ID/body before returning the v4 intent DTO:

```json
{"data":{"asset":{"id":"uuid","mediaType":"image","kind":"cover","state":"pending","version":1,"displayName":"tour.jpg","sourceBytes":8500000,"storedBytes":null,"sourceMime":"image/jpeg","storedMime":null,"altText":null,"createdAt":"ISO","updatedAt":"ISO","previewAvailable":false,"referenceCount":0,"failure":null},"uploadId":"uuid","uploadPath":"brands/{org}/assets/{assetId}/{nonce}.source","handleUploadUrl":"/api/v1/organizers/{org}/assets/client-upload","expiresAt":"ISO","usage":{},"capabilities":{}},"error":null}
```

`usage` and `capabilities` have the exact v4 `UsageSummary` and `MediaCapabilities` shapes; `{}` above is illustrative shorthand, never an actual response. The server-generated `uploadPath` is visible only to the authenticated owner for the SDK transfer. The token allows only that path and exact declared `sourceMime`, sets `maximumSizeInBytes=sourceBytes` (not 10,000,000), cannot overwrite, and expires after 10 minutes. A smaller file can complete; the browser cannot alter the reserved size or MIME under the same `uploadId`. The existing `POST /assets` multipart image write is retired/disabled before image upload is enabled; it must never silently accept a file over the Function limit. A2 draft attachment remains a separate brand-scoped, versioned action after status is `ready`.

The browser keeps its `File` and `uploadId` across recoverable network errors, calls SDK `upload()`, then polls `GET /assets/{assetId}/status`. The SDK's progress and success are **source transfer status**, not normalized asset readiness or draft attachment. The list/status routes expose `pending|uploading|verifying|ready|failed|deleting` after reload. Unknown global usage or callback verification failure disables new intents but keeps list/recovery visible.

## Physical storage and accounting

Migration 005 adds `source_blob_path`, `normalized_blob_path` (or maps the normalized path to the existing `private_blob_path`), `source_verified_bytes`, `normalized_verified_bytes`, and a processing claim/version. Both source and normalized Blobs are private, server-generated, and retained for a **successful ready image until explicit organizer deletion**. They count against shared store usage for their full lifetime. This follows the approved source-photo retention; normalization does not silently discard the source. For video, the single verified video Blob continues to count once.

Before a direct image token is issued, the global ledger transaction reserves **`sourceBytes + 5,000,000` bytes** and one image item slot. It checks `observedStoredBytes + outstandingReservations + thisReservation <= 950,000,000`, counting every brand, legacy/untracked Blob and participating writer. A source declared as 8.5 MB therefore needs up to 13.5 MB free even though the final normalized output may be smaller. The reservation is not just `sourceBytes`; source and output can coexist. At callback, verify the source `head()` path/MIME/size; `head().size > sourceBytes` fails/quarantines while bytes remain charged until confirmed deletion. A smaller source reduces the source-side reservation only after verification, while the 5 MB output allowance remains. After normalized write, verify its path, MIME, dimensions and `head().size <=5,000,000`, then atomically replace the reservation with **actual source bytes + actual normalized bytes**. Never subtract the source simply because normalization succeeded. Ledger reconciliation counts each physical path once and catches orphaned source/output Blobs.

During output write, the reserved 5 MB covers the additional Blob even if the source already exists. If normalization fails, do not mark ready; keep source bytes charged and move to a visible `failed` or `verifying` recovery state. Failed partials may be removed only after confirming they were never ready, are unreferenced, and a complete Blob head/list reconciliation proves deletion. If normalization succeeds but status commit is uncertain, keep both Blobs and the reservation until recovery finds the final state; do not generate a second output Blob on a retry. A deterministic output path and processing claim make callback retries converge. Only ready assets can attach to drafts or public events. Explicit deletion removes both source and normalized Blobs, confirms each removal, then releases their actual bytes; partial delete remains `deleting`, charged and retryable. Public image delivery continues from the normalized Blob through the A4 media route. Private source is never a public preview.

## Server processing and safety

The callback independently rechecks the token, owner/brand and intent, then verifies `head()` before processing. The processor reads only the deterministic private source path; it limits input to 10 MB, decoded pixels to 12 million, width/height to 4,096, and rejects malformed or polyglot data. Decode and re-encode with EXIF/GPS/metadata stripped, orientation applied, and a bounded effort/quality ladder. If output cannot fit 5 MB while remaining a usable image, fail with `IMAGE_OUTPUT_TOO_LARGE`; do not truncate or claim success. Use image libraries only server-side. The Function may download/process at most one bounded 10 MB source in memory or stream as supported, then writes output directly to Blob; its inbound/outbound HTTP body remains small. Set a bounded processing timeout and a single-flight DB claim so duplicate callbacks cannot run two normalizations. No untrusted filename or user-supplied path reaches Blob operations.

`AssetSummary` retains v4 fields; for images `sourceBytes` is the declared browser source size, `storedBytes` is verified normalized size, and `previewAvailable` is true only when normalized ready. Add `sourceStoredBytes:number|null` to show verified original bytes, and `storageBytes:number|null` to show the **sum** of retained source and normalized bytes. These values are null until verified; the server remains authoritative for actual shared usage. `UsageSummary.observedStoredBytes` already includes both objects. The UI can display “processing image” after SDK completion and “ready to attach” only after `ready`. No public raw source URL is returned.

Failure codes extend v4 with 422 `IMAGE_DECODE_FAILED`, 422 `IMAGE_OUTPUT_TOO_LARGE`, 503 `IMAGE_PROCESSING_UNAVAILABLE`, and recoverable `IMAGE_PROCESSING_RETRY` in `AssetSummary.failure`; `UPLOAD_VERIFICATION_FAILED`, `STORAGE_USAGE_UNKNOWN`, `SHARED_STORE_FULL` and exact `UPLOAD_ID_CONFLICT` remain. A retry of unchanged `uploadId` returns the same intent and asset; changed parameters return 409. Status reads never trigger an unbounded hidden reprocess. A bounded recovery worker or explicit retry endpoint can claim the same deterministic source/output paths and resume, with no duplicate item slot or output Blob. The exact retry route, if added, must be agreed with Frontend before implementation; otherwise automatic recovery is server-owned and the UI offers a status refresh.

## Verification and release gate

Tests must cover declared 1 MB versus attempted 10 MB token abuse, exact token size, source smaller than declaration, two brands racing for shared bytes, source+output coexistence, missing/incomplete all-prefix inventory, untracked/legacy Blobs, normalization output too large, metadata stripping, malicious oversized dimensions, callback duplication/loss, partial output write, uncertain finalization, source and output deletion failures, and unchanged-ID retry. A connected test must upload a >4.5 MB image directly from the browser, see it normalized and attached in an A2 draft, publish an A4 listing with its server image, confirm both physical sizes and global usage, and then verify delete/reference rules. Keep `imageUploadEnabled=false` and the old multipart write disabled until all-writer accounting, processor and connected tests pass. Video upload and public playback retain separate capability gates.

No A3 app code, Blob object, environment secret or external service was changed by this contract. The PM should send this v5 to Frontend for agreement before implementation.
