# Integrated Phase A3 media v3 — shared free Blob and video proposal

Date: 2026-10-21. **Prospective; no code or service changed.** Source: `brief/project.json` v104, `integration/design/brand-media-v1.md`, and A3 v2. This supersedes A3 v2 where it assumed image-only uploads, 100 MiB per brand, or ten hourly uploads. Frontend agreement and PM handoff precede implementation. A1 Clerk identity, A2 brand drafts, A3 transactional draft references, and A4 immutable public media references remain the foundation. The current A3 upload/delete write gate remains **off**.

## Approved limits and honest availability

Each brand may have at most **100 images and 10 videos**. Each video source is at most **100,000,000 bytes** (decimal 100 MB). These are **item maxima, not reserved storage allocations**: ten 100 MB videos would already exhaust a nominal 1 GB allowance before images, other brands or legacy blobs. The owner chose the free Vercel Blob plan and asked uploads to stop before its shared 1 GB included storage is exhausted. Vercel's current Hobby pricing lists 1 GB-month of Blob storage and says Blob access stops if Hobby usage limits are exceeded; this is not a real-time 1 GB hard quota API. [Vercel Blob usage and pricing](https://vercel.com/docs/vercel-blob/usage-and-pricing). The application therefore enforces a conservative **950,000,000-byte admission ceiling** (50 MB headroom) across every blob in the connected private store, including older demo objects and untracked paths, plus outstanding reservations. The displayed remaining bytes are a recent measured estimate, never a guarantee of future upload success.

The 950 MB threshold is a proposed operational safety setting, not a change to the owner's 1 GB requirement. It can only be enabled after a complete store inventory and exclusive accounting of **every writer** to that store. Existing anonymous demo listing/artwork writes may share it; unless they participate in the same global reservation ledger or are disabled/moved to a separately accounted store, A3 admission **fails closed**. A scan does not make external concurrent writes safe. If the store, usage list, or ledger reconciliation is unavailable or incomplete, show `storageStatus:"unknown"`, disable new upload intents, and return 503 `STORAGE_USAGE_UNKNOWN`. Do not infer free space from only A3's SQL rows or claim that the dashboard's averaged usage is instantaneous free bytes.

## Canonical media and storage ledger

Migration 005 extends `organizer_media_assets`: `mediaType:image|video`, `kind:business|event-location|cover|event-video|poster` (poster is an image), `sourceMime`, `storedMime`, `sourceBytes`, `storedBytes`, `state:pending|uploading|verifying|ready|failed|deleting|deleted`, `version`, server-generated opaque `private_blob_path`, upload claim ID, request hash, reservation bytes, expiration, verified checksum/ETag if available, and timestamps. Successful `ready` images/videos remain until explicit organizer deletion. `pending/uploading/verifying/deleting` count toward brand item slots and global reserved bytes; `ready` counts actual stored bytes. A failed intent releases bytes **only after** proving no uncommitted Blob remains. A failed delete stays visible and charged until Blob deletion is confirmed.

`blob_store_usage` is one locked row per connected store ID with `lastFullScanAt`, `observedBytes`, `managedReadyBytes`, `untrackedBytes`, `reservedBytes`, `reconciliationStatus`, and a monotonically increasing generation. Full reconciliation uses private-store `list({cursor,limit,mode:'expanded'})` until `hasMore=false`; each result includes `size` and `pathname`. It includes all prefixes, not just `brands/`. [Vercel Blob SDK list and pagination](https://vercel.com/docs/vercel-blob/using-blob-sdk). Compare the scan with Neon asset rows and any legacy writer ledger, counting each physical pathname once. Duplicate/missing paths, an unfinished scan, a changed store ID, or stale snapshots force `unknown` and block admission. The snapshot must be refreshed within a bounded interval before an upload claim, and a single SQL transaction locks the ledger row while reserving the **declared maximum source bytes**. No two A3 intents can oversubscribe it. A fresh scan is necessary but insufficient when nonparticipating writers still exist; they must be brought under the ledger or paused first. Verified deletions reduce reservations after a new `head`/list confirmation; a 404 alone is reconciled against the expected path before freeing bytes.

For the UI, `GET /api/v1/organizers/{org}/assets/usage` returns `{data:{imageCount,videoCount,imageLimit:100,videoLimit:10,observedStoredBytes,reservedBytes,sharedRemainingBytes,storageStatus:"ready|unknown|full",checkedAt},error:null}`. `sharedRemainingBytes` is `null` when unknown; it is never computed client-side. It discloses no other brand identity or path. An authenticated active member can read; only an owner can request uploads/deletes until staff-role implementation changes.

## Image and video admission

Image size and encoding rules from A3 v2 are **not carried forward as approved limits**. Before image uploads can be enabled, PM must settle a bounded source-byte cap and output normalization with Frontend. The eventual server image path may continue to decode, strip metadata and re-encode under a verified output cap; browser file type/name alone is insufficient. Business and distinct event-location slots still require images for publication. Existing ready images retain their references; do not delete or reinterpret them during migration.

For video, avoid sending up to 100 MB through a Vercel Function. Use `@vercel/blob/client` `upload()` directly from the browser to the **private** store, with a server `handleUpload` token route. Vercel documents private client uploads, bounded `maximumSizeInBytes`, `allowedContentTypes`, token payload and a completion callback. [Vercel client uploads](https://vercel.com/docs/vercel-blob/client-upload), [SDK token options](https://vercel.com/docs/vercel-blob/using-blob-sdk). The upload destination pathname must be a server-generated opaque `brands/{org}/assets/{assetId}/{nonce}.video` from an already reserved intent. The browser necessarily sees this **private upload pathname** and the SDK's private Blob result; this narrowly revises A3 v2's “path never exposed” rule. It is not a public playback URL or permission to choose arbitrary paths. Never render it on a public page or persist a client-supplied URL as authoritative.

Proposed route sequence, all JSON using `{data,error}` except the SDK token/callback exchange and binary media:

| Route | Request | Result |
| --- | --- | --- |
| `POST /api/v1/organizers/{org}/assets/upload-intents` | Same-origin JSON `{uploadId:UUID,mediaType:"video",kind:"event-video",sourceName:string,sourceMime:string,sourceBytes:integer,eventId:UUID|null}`; video bytes 1–100,000,000. | 201 `{assetId,uploadId,uploadPath,handleUploadUrl,expiresAt,state:"pending",usage}`. Stable replay returns same intent; changed parameters with same ID: 409. |
| `POST /api/v1/organizers/{org}/assets/client-upload` | SDK `handleUpload()` token/completion protocol. Token callback independently authenticates owner, checks reserved intent, exact pathname, type, max bytes, expiry and ledger state. | SDK response only; no normal app envelope. The callback never trusts browser-provided brand, event or asset metadata. |
| `GET /api/v1/organizers/{org}/assets/{assetId}/status` | Authenticated active member. | 200 `{asset:AssetSummary,usage}` with `pending|uploading|verifying|ready|failed|deleting`. The browser polls this after the SDK upload succeeds. |
| `GET /api/v1/organizers/{org}/assets` | Existing bounded pagination plus `mediaType` filter. | Ready and deleting records, no private path/URL. |
| `GET /api/v1/organizers/{org}/assets/{assetId}` | Active member. | Server-streamed private image or video preview only when ready; `Range` handling is separate below. |
| `GET /api/v1/organizers/{org}/assets/{assetId}/references` and `DELETE /assets/{assetId}` | Existing A3 brand-scoped reference and owner `If-Match`/confirm-delete semantics, extended to published events and videos. | 409 `ASSET_IN_USE` includes draft/public reference locations; delete 204 only after verified Blob removal. |

The token allows only the reserved MIME family and `maximumSizeInBytes=100000000`, expires quickly (proposed 10 minutes), and cannot overwrite. Prefer an exact MIME allowlist after owner format decision; do not use `video/*` in production. `onUploadCompleted` verifies the SDK callback and token payload, then checks exact path and Blob `head()` size/content type. A server-side bounded signature/header probe must reject a file whose bytes do not match its claimed container; codec playability cannot be inferred from MIME or filename. The app must not mark `ready` or attach a video until this verification passes. The callback can arrive before the browser receives success, can retry, or can be missing locally; status polling/reconciliation handles each case without duplicate assets. Local development callback needs a reachable test URL; without it, do not claim a successful local end-to-end video upload. [Vercel callback behavior](https://vercel.com/docs/vercel-blob/client-upload).

## Races, failures and retention

Reserve one brand item slot plus declared bytes in Neon **before** token generation. Replays of an unchanged `uploadId` return the same intent and do not reserve again. The browser retains the File and `uploadId` through a network retry. A token request for any other pathname, expired intent, changed media type/size or disabled membership is denied. At completion, transition `pending/uploading → verifying → ready` in a transaction only if path, size and verified MIME match; replace declared-byte reservation with actual bytes. If upload fails before Blob creation, mark failed and release the reservation. If Blob exists but finalization is uncertain, keep the reservation and `verifying` state until `head()` and ledger reconciliation resolve it. A bounded recovery task may remove **only never-ready, expired partial uploads** after checking they are not referenced and cannot have been finalized. It must never remove ready, unattached, cancelled-event or historical receipt media automatically.

Explicit delete locks the same asset row used by attachment. It is rejected while any A2 draft, A4 public event, poster or later immutable receipt snapshot references the asset. A cancelled public event still counts. Published-event replacement is a future versioned edit action requiring owner review; old media remains while any old confirmation or published version refers to it. If Blob deletion fails, retain `deleting`, charge its bytes and expose retry. If the delete result is uncertain, check the deterministic path before marking `deleted`. The A3 v2 recovery rule for source device images remains: importing or attaching never discards the local original.

## Public image and video delivery

Public images continue through A4's server-approved `/api/v1/events/{eventId}/media/{slot}` route, not a raw private Blob URL. Event-video placement, format, poster and captions remain product decisions. Until those are agreed and playback is verified, **store videos privately only** and hide the public video module; an event may still publish with its required images. If later enabled, use `/api/v1/events/{eventId}/media/video` resolved from immutable public references. Validate event status/asset state and allowlisted MIME on every request. Implement `HEAD`, full `GET`, and **one bounded bytes range** (`Range: bytes=start-end` or suffix) with correct `206 Content-Range`, `Content-Length`, `Accept-Ranges: bytes`, or `416 Content-Range: bytes */size`; reject multi-range and malformed ranges. Vercel documents Blob range support and `get()` accepts additional request headers, but the private-store range path and response headers must be proven with the connected store before enabling the player. [Vercel range example](https://vercel.com/docs/vercel-blob/examples), [SDK get options](https://vercel.com/docs/vercel-blob/using-blob-sdk). Never respond `200` with a full 100 MB body to a valid range request. Stream; do not buffer the whole video in a Function. Keep a stable aspect ratio, native accessible controls and a poster/fallback; no autoplay with sound. Account for Blob Data Transfer and Function Fast Data Transfer separately from storage, as private delivery uses both. [Vercel private delivery costs](https://vercel.com/docs/vercel-blob/private-storage).

## Release gates and ownership

Frontend owns the brand media library and contextual slot upload, progress, status polling, honest shared-byte display, retry and explicit detach/delete, following `integration/design/brand-media-v1.md`. Backend owns migration 005, global ledger and complete-store reconciliation, all-writer coordination, token authorization and callback verification, video MIME/byte validation, reference-safe delete and private streaming. They must agree exact DTOs and recovery copy before code. Tests must simulate two brands racing for the last bytes, legacy/untracked blobs, incomplete list pages, callback retry/loss, unknown Blob outcome, token path substitution, oversized/wrong-type video, referenced delete, failed delete retry, and private byte ranges. A connected test must inspect actual Blob listing/size, token callback, private Range 206/416, and dashboard usage before lifting the feature gate.

**Decisions still for PM, one at a time:** image source/output size; exact accepted video container/codecs and whether public playback is in this free-plan iteration; poster/captions rule; rate/concurrent intent caps; future published-media replacement behavior. The already approved 100-image/10-video item maxima, 100 MB video maximum, free shared Blob constraint, and successful-asset retention are not reopened. If accurate whole-store accounting or private video delivery cannot be verified, keep uploads/playback disabled and report the limit. No A3 code or external storage was changed by this proposal.

## V4 amendments — authoritative where v3 differs

This v4 supersedes v3 and incorporates `frontend/integrated-phase-a3-media-v3-review.md`. The detailed v3 ledger, security, retention and delivery rules still apply except where this section changes them. This is prospective; no code or connected store was changed.

### Admission, actual bytes and token scope

Image source max **10,000,000 bytes**. Decode and normalize to JPEG, PNG or WebP with metadata stripped and output <= **5,000,000 bytes**; reject if safe normalization cannot meet the bound. A video source max is **100,000,000 bytes** and initially accepts MP4 with H.264 video and AAC audio, verified from actual file bytes/codec inspection. Poster/captions are optional. Public player has no autoplay and stays gated until a connected private-range test passes. The 100 image/10 video brand maxima and 950,000,000-byte conservative shared-store admission ceiling remain.

An intent's `sourceBytes` is immutable for its `uploadId`. The client-upload token's `maximumSizeInBytes` **equals that exact reserved sourceBytes**; it never uses the 100,000,000-byte class maximum for a smaller reservation. The completion callback verifies `head().size <= sourceBytes`; excess size fails/quarantines the asset and remains charged until confirmed removal. A smaller actual file is accepted after MIME/codec verification, then the reservation becomes actual stored bytes and the difference is released transactionally. Changed source size for the same ID returns 409 `UPLOAD_ID_CONFLICT`. The existing all-writer reconciliation and unknown-usage fail-closed gate remain mandatory.

Per-brand operational limits are 10 new intents per rolling hour and 2 concurrent pending/uploading/verifying intents, counting image and video together. Same-ID retries do not consume another slot. These defaults are configurable downward; 429 `UPLOAD_RATE_LIMITED` carries `Retry-After` only when an actual retry time is known. Capacity/concurrency responses must distinguish their cause.

### Exact projections

`UsageSummary = {imageCount,videoCount,imageLimit:100,videoLimit:10,observedStoredBytes,reservedBytes,sharedRemainingBytes:number|null,storageStatus:"ready"|"unknown"|"full",checkedAt:ISO|null}`. Counts include pending/ready/deleting as v3 describes; `sharedRemainingBytes` is null when unknown.

`MediaCapabilities = {imageUploadEnabled:boolean,videoUploadEnabled:boolean,videoPlaybackEnabled:boolean,reasonCode:string|null,reason:string|null}`. `GET /api/v1/organizers/{org}/assets/usage` returns `{data:{usage:UsageSummary,capabilities:MediaCapabilities},error:null}`. Server capabilities are authoritative; a public env flag may only disable controls further. Unknown usage disables intents, while authorized list/preview/delete remain available.

`AssetSummary = {id,mediaType:"image"|"video",kind,state,version,displayName,sourceBytes,storedBytes:number|null,sourceMime,storedMime:string|null,altText:string|null,createdAt,updatedAt,previewAvailable:boolean,referenceCount:number,failure:{code,message}|null}`. Display name is sanitized and bounded. No private path, raw token, Blob URL, other-brand information or internal error is returned. A status-by-ID response returns `{data:{asset:AssetSummary,usage:UsageSummary,capabilities:MediaCapabilities},error:null}`. An intent returns 201 `{data:{asset:AssetSummary,uploadId,uploadPath,handleUploadUrl,expiresAt,usage:UsageSummary,capabilities:MediaCapabilities},error:null}`. The uploadPath is exposed only in the owner-authenticated intent response for the SDK transfer, never in list/status/public DTOs.

`GET /api/v1/organizers/{org}/assets?limit=20&cursor=...&mediaType=...&state=...` returns `{data:{assets:AssetSummary[],nextCursor,usage:UsageSummary,capabilities:MediaCapabilities},error:null}`. Limit 1–50, default 20; newest `createdAt` then UUID, opaque cursor bound to filters and brand. Include pending, uploading, verifying, failed, ready and deleting by default so a different device can recover. Deleted only when explicitly filtered. Status route remains the polling authority.

Error envelope follows A1–A4 `{data:null,error:{code,message,fields?}}`. Codes: 422 `BRAND_IMAGE_LIMIT`/`BRAND_VIDEO_LIMIT` (`mediaType`); 413 `IMAGE_SOURCE_TOO_LARGE`/`IMAGE_OUTPUT_TOO_LARGE`/`VIDEO_SOURCE_TOO_LARGE` (`sourceBytes`); 422 `UNSUPPORTED_MEDIA_FORMAT` (`sourceMime`); 409 `UPLOAD_ID_CONFLICT` (`uploadId`); 410 `UPLOAD_EXPIRED`; 422 `UPLOAD_VERIFICATION_FAILED`; 507 `SHARED_STORE_FULL`; 503 `STORAGE_USAGE_UNKNOWN`/`MEDIA_UNAVAILABLE`; 429 `UPLOAD_RATE_LIMITED`. Safe failure code/message persists on failed asset summary after reload. SDK callback errors retain SDK protocol, not this app envelope.

### Video placement and release behavior

`kind:"event-video",eventId:null` creates an unassigned **private brand-library video**. A non-null brand-owned eventId records intended context only; it does not attach or publish video. The A2 draft DTO has no video slot, and A4 public event detail has no video placement. A later versioned placement contract must define media reference, poster/caption representation and history before public video UI can appear. An uploaded video can be inspected privately once ready, but the UI must not imply public playback or event attachment.

Do not update the existing A3 image-only UI bounds or show upload controls until this v4 contract receives Frontend agreement and a PM handoff. All write/playback gates stay off until complete store reconciliation, callback, private range and browser-to-data checks pass. Successful assets stay until explicit organizer deletion; partial never-ready objects may be cleaned as in v3.
