# Integrated Phase A3 media v6 — temporary image source amendment

Date: 2026-10-21. Source: `brief/project.json` v104, PM handoff 008, `contract/integrated-phase-a3-media-v5.md`, and `frontend/integrated-phase-a3-media-v5-review-v1.md`. **Prospective; no app code or service changed.** This v6 supersedes v5 only where v5 retained the raw source image after successful normalization. All v4/v5 limits, direct browser upload DTOs, owner authorization, all-writer ledger, feature gates, and video rules remain. Frontend agreement and PM handoff must precede implementation.

## Image lifecycle and reference invariant

The uploaded private source Blob is a **temporary processing input**. The verified normalized private Blob is the durable event photo, retained until the organizer explicitly deletes the asset, subject to reference checks. The original `File` on the user’s device is never deleted or modified by this server cleanup. The source path must never enter an A2 draft reference, public A4 event reference, receipt snapshot, or public image response. A migration/reconciliation check blocks cleanup of any pre-existing source path with a durable reference until that reference is safely moved to the verified normalized asset; it must not blindly delete a referenced Blob.

The client reserves one image slot and **`sourceBytes + 5,000,000` bytes** under the shared 950,000,000-byte ceiling before receiving a direct upload token. The token still restricts `maximumSizeInBytes` to the exact declared source size. The callback verifies source path, MIME and actual bytes, then decodes, strips metadata, normalizes and uploads an image no larger than 5,000,000 bytes. Before committing `ready`, the server verifies the normalized `head()` path, MIME, dimensions, absence of sensitive metadata, size and checksum/ETag when the Blob service provides one. A deterministic normalized path and single-flight processing claim prevent duplicate output on callback retry. The transaction commits the normalized path as the asset’s authoritative preview/attachment/public path **before** any raw-source delete is attempted. A ready image remains usable even if source cleanup fails.

## Ledger states and cleanup

While the source and normalized Blobs coexist, charge **both actual physical byte counts**. `ready` means the normalized Blob is verified and referenceable; it does not assert source cleanup. Immediately after the ready commit, queue/claim idempotent source cleanup using the image asset ID, source path and a cleanup generation. Deletion may run synchronously after commit or in a bounded retry worker, but never inside a transaction that can roll back the ready asset after the Blob was deleted. Confirm the source is absent with `head()` or a complete store reconciliation before subtracting its bytes. A timeout, uncertain delete, or stale/incomplete inventory keeps `sourceCleanupPending=true`, charges the source and retries the same deterministic path. It never deletes or downgrades the normalized ready image. A `404` from Blob alone is reconciled with the expected path and ledger generation before release. Once confirmed absent, set `sourceStoredBytes=0`, `sourceCleanupPending=false`, and steady-state `storageBytes=normalizedVerifiedBytes` in the same locked ledger/asset transaction.

If normalization fails before ready, source and any partial output remain charged until verified cleanup of never-ready objects. If ready commit outcome is uncertain, reconcile asset state and both paths first; never perform source cleanup merely because the callback did not receive a response. A callback retry seeing ready must skip re-encoding and resume only pending cleanup. Explicit organizer delete checks all draft/public/receipt references, then removes the normalized Blob and any residual source, confirms each absence, and releases each physical byte count. A failed/uncertain delete remains visible as `deleting`, with any physical bytes still charged. All-writer global reconciliation continues to count every path once, including older demo objects and other brands; stale or unknown usage keeps new intents disabled.

## Exact DTO amendments

The v5 `AssetSummary` adds `sourceCleanupPending:boolean` for images. `sourceBytes` remains the **declared** browser upload size. `sourceStoredBytes:number|null` is the **currently retained, verified source bytes**; it becomes `0` only after confirmed source cleanup. `storageBytes:number|null` is the sum of the currently retained source and normalized physical Blob bytes. A ready image with cleanup pending may show `sourceStoredBytes>0`, `storageBytes=sourceStoredBytes+storedBytes`, and `previewAvailable:true`. After cleanup it shows `sourceStoredBytes:0`, `storageBytes:storedBytes`, and `sourceCleanupPending:false`. While physical outcome is uncertain, byte fields may remain last-verified values and `UsageSummary.storageStatus` becomes `unknown`; do not imply released capacity. For videos, `sourceCleanupPending:false`, `sourceStoredBytes:null`, and `storageBytes` equals the verified video Blob size. No raw source path, URL, filename metadata or source bytes are emitted in public storefront/event/ticket DTOs. Private owner status/list may show only numeric accounting and cleanup state.

The existing status and list envelope includes this `AssetSummary`; no new browser cleanup action is required. A safe `SOURCE_CLEANUP_PENDING` informational state may accompany `ready` if the UI wants to show “Source cleanup pending”; it must not block preview or attachment. A cleanup failure is not an asset failure once normalized ready is committed. The old multipart Function upload remains disabled. `imageUploadEnabled` remains false until direct transfer, normalization, full-ledger accounting and browser/API/Blob verification pass.

## Verification before activation

Test the source+5 MB reservation against two brands racing for remaining shared space; token maximum versus declared bytes; normalized verification before ready; metadata removal; a callback replay that does not create a second normalized Blob; ready-image preview/attachment/public delivery during failed source cleanup; exact usage before and after confirmed source removal; callback/cleanup/explicit-delete races; stale ledger generation; a source path with a legacy durable reference; and no source path or bytes in public DTOs. Connected verification must upload an image larger than the Function body cap via the browser, observe both physical paths temporarily, confirm normalized publication, then confirm raw path removal and reduced ledger usage. Keep gates off if any of these cannot be verified.

This change resolves Frontend’s v5 objection while preserving the owner’s instruction that successful private photos remain until explicit deletion: the normalized photo remains; only the temporary server upload is cleaned.
